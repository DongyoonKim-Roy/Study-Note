# SQLi
## 1. What is SQLi (SQL Injection)?
`SQL injection`은 공격자가 어플리케이션의 `데이터베이스 쿼리`에 `간섭`할 수 있게 하는 보안 결함 임. 공격자는 다른 사용자의 정보나 어플리케이션에서 사용할 수 있는 모든 데이터를 비롯해 접근 권한이 없는 데이터를 `조회`, `수정` 또는 `삭제` 가능. 이러한 행위는 어플리케이션의 기능이나 콘텐츠를 영구적으로 변경하거나, 서버를 침해하거나, 서비스 거부를 일으킬 수 있음.

예를들어 웹사이트가 아래와 같이 동작 한다고 할 때
- 사용자가 로그인, 검색, 상품 보기 같은 행동을 함
- 웹사이트가 그 정보를 데이터베이스에 물어봄
- 데이터베이스가 답을 주면 화면에 보여줌

이때 웹사이트가 사용자가 입력한 내용을 `제대로 확인하지 않고` 그대로 데이터베이스에 넘기면 문제가 생김.

비유:
식당에서 손님이 주문지에 
"김치찌개 하나"라고 적어야 하는데
"김치찌개 하나, 주방 금고 비밀번호, 매출 전표" 라고 적음
그런데 주방장이 주문지를 `확인도 안 하고` 그대로 실행해 버리는 상황.

로그인 예시:
```
SELECT * FROM users WHERE username = 'usernameInput' AND password = 'passwordInput';
```
이때 어플리케이션이 입력값을 `제대로 검증하지 않고` 쿼리에 그대로 붙여 넣으면, 공격자가 SQL 문법 자체를 조작 가능.

공격자가 비밀번호 칸에 다음과 같이 입력한다고 가정.
```
' OR '1'='1
```
실제 실행되는 쿼리
```
SELECT * FROM users WHERE username = 'usernameInput' AND password = '' OR '1'='1';
```
`'1'='1'` 은 항상 참이기 때문에, 비밀번호가 틀려도 로그인 우회 가능.

**쉽게 비유하면**
- 정상적인 웹사이트 = 식당에서 손님이 주문한 메뉴만 정확히 만들어 주는 것
- SQLi가 있는 웹사이트 = 손님이 주문지에 "음식 말고도 주방에 있는 전체 메뉴와 금고에 있는 돈도 가져와"라고 적었는데, 주방장이 그대로 실행하는 것

**핵심**
- SQLI는 웹사이트가 사용자 입력을 SQL 쿼리에 그대로 넣어서 발생
- 브라우저가 아닌 `데이터베이스`를 직접 조작
- 데이터 탈취, 변조, 삭제, 경우에 따라 서버 명령 실행까지 가능

---
## 2.SQLi를 통해 가능한 공격들
공격자는 데이터베이스에 보내는 쿼리를 조작할 수 있음.

**실제로 할 수 있는 일들**
- 데이터 열람 : 다른 사용자의 개인정보, 비밀번호 해시, 신용카드 정보 등 조회
- 인증 우회 : 로그인 없이 관리자 계정으로 접속
- 데이터 변조/삭제 : 다른 사람의 정보 수정, 레코드 삭제
- 권한 상승 : 일반 사용자 계정을 관리자 권한으로 변경
- 데이터베이스 서버 장악 : 일부 DBMS에서 OS 명령 실행 (`xp_cmdshell`, `LOAD_FILE` 등)
- 다른 시스템으로 확장 : 내부 네트워크 정보 수집 후 추가 공격

## 3. SQLi 유형
### 3.1 Error-based SQLi
웹사이트가 데이터베이스와 통신하다 `에러가 발생했을 때`, 그 에러 메시지를 사용자에게 그대로 보여주면서 생기는 취약점.\
정상적인 경우에는 에러 메세지는 개발자만 봐야 하지만,\
일부 사이트는 "에러가 났습니다" 같은 메시지 안에 `데이터베이스가 반환한 원본 에러`를 그대로 출력 함.\
공격자는 이 점을 이용하여 `의도적으로 에러를 발생`시키고,\
에러 메시지 안에 들어 있는 정보를 읽어냄.\

**왜 가능한가?**
- 데이터베이스가 반환하는 `에러 메세지`를 통해 정보를 추출
- 에러에 테이블명, 컬럼명, 데이터 일부가 포함되는 경우

**예시**
로그인 예시:
```
SELECT * FROM users WHERE username = 'usernameInput' AND password = 'passwordInput';
```

공격자가 username 칸에 다음과 같이 입력한다고 가정.
```
' AND 1=CONVERT(1,@@version) -- -
```

실제 실행되는 쿼리
```
SELECT * FROM users WHERE username = '' AND 1=CONVERT(int, @@VERSION) -- - AND password = 'passwordInput';
```
**쿼리 설명**
| 부분     | 의미                | 설명    |
| ------ | ------------------------- | ---------------- |
| `'`  | 문자열 닫기                   | 원래 쿼리의 따옴표를 닫아서 SQL 문법 탈출          |
| `AND 1=`  | 조건 추가            | 뒤에 오는 값과 비교하도록 만듦 |
| `CONVERT(int, ...)` | 강제 형변환   | 문자열을 숫자로 바꾸려고 시도 -> **에러 발생**  |
| `@@version`  | 버전 조회         | 데이터베이스 버전 정보를 가져옴       |
| `-- -` | 주석 처리 | 뒤에 남은 원래 쿼리를 무시        |

**실행흐름**
1. 공격자가 입력값에 위 페이로드를 넣음
2. 데이터베이스가 `@@version` 값을 가져옴
3. 이 version 정보를 `CONVERT(int, ...)`로 **숫자로 바꾸려고** 시도
4. 문자열은 숫자가 될 수 없으므로 **에러 발생**
5. 에러 메세지에 버전 정보가 포함되어 화면에 출력됨
6. 공격자는 메세지에서 정보를 그대로 읽어냄

**얻을 수 있는 정보**
- 데이터베이스 종류와 버전
- 데이터 베이스 이름
- 테이블 목록
- 컬럼 목록
- 실제 데이터

**장점과 한계**

**장점**
- 직관적이고 빠름
- 한 번의 요청으로 정보를 바로 확인 가능
- 결과가 화면에 출력되지 않아도 사용 가능

**한계**
- 웹사이트가 `에러 메세지를 숨기면` 사용불가
- 최신 웹 어플리케이션은 대부분 에러를 사용자에게 보여주지 않음
- DBMS마다 에러를 유발하는 문법이 조금씩 다름

### 3.2 Union-based SQLi
웹사이트가 데이터베이스에서 가져온 결과를 **화면에 그대로 출력**할 때 생기는 취약점.\
정상적인 경우에는 사용자가 요청한 데이터만 보여줘야 하지만,\
일부 사이트는 입력값을 제대로 검증하지 않아서 `UNION`이라는 문법으로 **다른 테이블의 데이터를 원래 결과에 강제로 붙일 수** 있다.\
공격자는 이 점을 이용해서
원래 보여주려던 결과 뒤에 자신이 원하는 데이터(다른 사용자의 정보, 비밀번호 등)를 붙여서\
**화면에 같이 출력**되게 만듬.
즉,\
**결과를 보여주는 화면을 이용해서, 원래는 볼 수 없는 데이터를 끌어와 보여주는 기법**.

정상 쿼리:
```
SELECT title, content FROM products WHERE id = 'idInput';
```

공격자 쿼리:
```
1' UNION SELECT username, password FROM users --
```

실제 실행되는 쿼리:
```
SELECT title, content FROM products WHERE id = '1' UNION SELECT username, password FROM users --
```

원래 상품 정보 결과에 **user 테이블의 username과 password** 가 뒤에 붙어서 같이 출력됨.\
즉, **화면에 결과가 출력되는 곳**을 이용해서 다른 테이블의 데이터를 끌어오는 기법임.

**조건**
`UNION`을 사용하려면 다음 두 가지 조건이 맞아야 함.
1. **컬럼 개수가 동일**해야 함
2. **각 컬럼의 데이터 타입이 호환**되어야 함
예를 들어 원래 쿼리가 3개 컬럼을 반환하는데,
`UNION SELECT` 쪽에서 2개만 반환하면 에러가 남.

**실행흐름**
1. 컬럼 개수 찾기\
  가장 많이 쓰이는 방법은 `ORDER BY` 임
```
' ORDER BY 1 -- -
' ORDER BY 2 -- -
' ORDER BY 3 -- -
' ORDER BY 4 -- -
```
`ORDER BY 3` 까지는 정상적으로 동작하고 `ORDER BY 4`에서 에러가 나면 -> **컬럼은 3개**라는 뜻임

다른 방법으로는 `UNION SELECT NULL` 을 하나씩 늘려가며 확인
```
' UNION SELECT NULL -- -
' UNION SELECT NULL, NULL -- -
' UNION SELECT NULL, NULL, NULL -- -
```
에러가 나지 않는 시점이 컬럼 개수임.

2. 어느 컬럼이 화면에 출력되는지 확인\
  컬럼 개수를 알았으면, 어떤 위치에 데이터를 넣어야 화면에 보이는지 테스트 함.
```
' UNION SELECT 'a', 'b', 'c' -- -
```
화면에 `a`, `b`, `c` 중 어떤 것이 보이는지 확인함.\
보이는 위치가 바로 **데이터를 출력할 수 있는 컬럼**임.

3. 실제 데이터 추출\
   출력 가능한 컬럼 위치에 원하는 데이터를 넣음.
```
' UNION SELECT username, password, NULL FROM users -- -
```
이렇게 하면 원래 결과 대신(또는 함께) `users` 테이블의 데이터가 나타남.

**실제 쿼리 예시**

원래 쿼리 : 
```
SELECT name, description FROM products WHERE id = '1';
```
공격 후 :
```
SELECT name, description FROM products WHERE id = '1' UNION SELECT username, password FROM USERS -- -;
```
화면에는 상품 정보와 함께(또는 대신) 사용자 계정 정보가 출력됨.

**자주 보이는 쿼리**
컬럼 수를 맞춘 상태에서 진행 해야함.
```
' UNION SELECT @@version, NULL, NULL -- -
' UNION SELECT database(), NULL, NULL -- -
' UNION SELECT table_name, NULL, NULL FROM information_schema.tables -- -
' UNION SELECT column_name, NULL FROM information_schema.columns WHERE table_name='users' -- -
```

**장점과 한계**

**장점**
- 한 번의 요청으로 많은 데이터를 가져올 수 있음
- 결과가 화면에 바로 보이기 때문에 직관적
- Blind 기법보다 훨씬 빠름

**한계**
- **결과가 화면에 출력되어야 함**
- 컬럼 수와 데이터 타입을 맞춰야 함
- 일부 필터나 WAF가 `UNION` 키워드를 차단하는 경우가 있음

### 3.3 Boolean-based Blind SQLi
웹사이트가 데이터베이스 결과를 **화면에 직접 보여주지도 않고**,\
에러 메시지도 **보여주지 않을 때** 사용하는 기법.\
정상적인 경우와 비정상적인 경우의 **페이지 내용이나 응답이 조금이라도 다르면**,\
공격자는 그 차이를 이용해서 데이터를 한 글자씩 추측해 나감.\
즉,\
**참일 때와 거짓일 때의 반응 차이를 보고, 원하는 정보를 한 글자씩 알아내는 기법**임.

**특징**
- 에러 메세지가 없어도 됨
- 결과가 화면에 출력되지 않아도 됨
- **참/거짓에 따라 페이지가 달라지는지**만 확인하면 됨
- 속도가 느림 (한 글자씩 확인해야 함)
- 거의 모든 상황에서 사용 가능해서 실전에서 자주 쓰임

**동작 원리**
로그인이나 상품 조회 페이지에서
입력값에 따라 "결과가 있다 / 없다" 또는 페이지 내용이 조금이라도 달라진다고 가정할때.

공격자는 다음과 같은 질문을 데이터 베이스에 던짐.
```
"admin 계정의 비밀번호 첫 글자가 'a'야?"
```
- 참이면 -> 페이지가 정상적으로 보임
- 거짓이면 -> 페이지가 달라지거나 "결과 없음:이 됨

이 차이를 보고 맞으면 다음 글자로 넘어가고,
틀리면 다른 글자를 시도하는 식으로 **한 글자씩** 알아냄.

**예시**
1. 차이 확인
  ```
  ' AND 1=1 -- -
  ' AND 1=2 -- -
  ```
2. 데이터 추출
  ```
  ' AND SUBSTRING((SELECT password FROM users WHERE username='admin'),1,1)='a'--
  ```
  - 페이지가 정상이면 -> 첫 글자는 `a`
  - 아니면 -> `b`, `c`, ... 를 차례로 시도
3. 길이 확인 후 반복
  ```
  ' AND LENGTH((SELECT password FROM users WHERE username='admin'))=32--
  ```
  길이를 먼저 알아낸 뒤, 한 글자씩 추출

**실제 예시**

정상 쿼리 :
```
SELECT * FROM products WHERE id = 'userInput';
```

공격자 쿼리 :
```
SELECT * FROM products WHERE id = '1' AND SUBSTRING((SELECT password FROM users WEHRE username='admin'),1,1)='a'--'
```
- 조건이 참이면 상품이 정상적으로 보임
- 조건이 거짓이면 상품이 안 보이거나 내용이 달라짐

이 차이로 비밀번호를 한 글자씩 알아냄.

**장점과 한계**

**장점**
- 에러도, 화면 출력도 필요 없음
- 거의 모든 환경에서 사용 가능
- Union이 막혀 있어도 동작하는 경우가 많음

**한계**
- 매우 느림 (요청 수가 많음)
- 페이지 차이를 자동으로 판별하는 도구가 필요함
- 음답이 완전히 동일하면 사용 불가 (이때는 Time-based로 전환)

**정리**

Blooean-based Blind SQLi는\
**참일 때와 거짓일 때의 페이지 차이를 이용해서, 데이터를 한 글자씩 추측하는 기법**임.\
눈에 띄게 빠르거나 직관적이지는 않지만,\
다른 방법이 모두 막혔을 때 **최후의 수단**으로 매우 강력함.

### 3.4 Time-based Blind SQLi
웹사이트가 결과를 화면에 보여주지도 않고,\
에러 메세지도 보여주지 않으며,\
참/거짓에 따라 페이지 내용조차 **전혀 달라지지 않을 때** 사용하는 기법임.

이때 공격자는 데이터베이스 에게\
"**조건이 참이면 몇 초 동안 기다려**" 라고 명령함.
- 조건이 참이면 -> 응답이 늦게 옴
- 조건이 거짓이면 -> 바로 응답이 옴

이 **시간 차이**만 보고 데이터를 한 글자씩 알아냄.

즉,\
"**응답이 느려지는지 아닌지를 보고, 원하는 정보를 추측하는 기법**" 임.

**특징**
- 페이지 내용이 전혀 변하지 않아도 됨
- 에러 메시지가 없어도 됨
- **응답 시간**만 측정하면 됨
- Boolean-based보다 더 느림
- 거의 모든 환경에서 최후의 수단으로 사용 가능

**동작 원리**
공격자는 다음과 같은 질문을 던짐.
> "admin 비밀번호 첫 글자가 'a'야?\
> 맞으면 5초 동안 기다리고, 아니면 바로 끝내"
- 응답이 **5초 이상** 걸리면 -> 맞음
- 응답이 **바로** 오면 -> 아님

이 방식으로 한 글자씩 확인.

**예시 흐름**
1. 시간 지연이 되는지 확인
  ```
  ' AND SLEEP(5) -- -
  ```
  - 응답이 약 5초 늦어지면 -> Time-based 가능

2. 데이터 추출
  ```
  ' AND IF(SUBSTRING((SELECT password FROM users WHERE username='admin'),1,1)='a', SLEEP(5), 0) -- -
  ```
  - 응답이 늦으면 -> 첫 글자는 `a`
  - 바로 오면 -> 다른 글자 시도

3. 길이 확인
  ```
  ' AND IF(LENGTH((SELECT password FROM users WHERE username='admin'))=32, SLEEP(5), 0) -- -
  ```

**실제 쿼리 예시**

정상 쿼리 :
```
SELECT * FROM products WHERE id = 'userInput';
```

공격 시 :
```
SELECT * FROM products WHERE id = '1' AND IF(SUBSTRING((SELECT password FROM users WHERE username='admin'),1,1)='a', SLEEP(5), 0) -- -'
```
- 조건이 **참**이면 -> 데이터베이스가 5초 대기 -> 웹사이트 응답이 느려짐
- 조건이 **거짓**이면 -> 바로 응답
공격자는 이 **느림 / 빠름**의 차이로 비밀번호를 알아냄.

**DBMS 별 지연 함수**
| DBMS | 지연 함수 | 예시 |
| --- | --- | --- |
| MySQL | SLEEP(5) | IF(조건, SLEEP(5), 0) |
| MSSQL | WAITFOR DELAY '0:0:5' | IF(조건) WAITFOR DELAY '0:0:5' |
| PostgreSQL | pg_sleep(5) | CASE WHEN 조건 THEN pg_sleep(5) END |

**장점과 한계**

**장점**
- 페이지 변화가 전혀 없어도 사용 가능
- 에러도, 출력도 필요 없음
- 다른 방법이 모두 실패했을 때 사용 가능

**한계**
- 가장 느림 (요청마다 대기 시간 발생)
- 네트워크 지연과 구분하기 어려울 수 있음
- 자동화 도구 없이는 현실적으로 힘듦

**정리**

Time-based Blind SQLi는\
"**조건이 참일 때만 의도적으로 응답을 늦춰서, 시간 차이로 데이터를 알아내는 기법**" 임.

가장 느리지만,\
**아무 반응이 없는 환경에서도** 정보를 추출할 수 있다는 점에서 강력한 최후의 수단임.

---
### 3.5 Stacked Queries
웹사이트가 데이터베이스 쿼리를 보낼 때,\
하나의 요청 안에 **여러 개의 SQL 문장을 연속으로 실행**할 수 있게 허용된 경우 생기는 취약점임.

정상적인 경우에는 사용자가 입력한 값으로 **하나의 쿼리**만 실행되어야 하지만,\
일부 환경에서는 세미콜론(;)을 이용해 쿼리를 끝내고 **새로운 쿼리를 추가로 실행**할 수 있음.

공격자는 이 점을 이용해서\
원래 쿼리 뒤에 자신이 원하는 **별도의 명령**을 붙여 실행함.

즉,\
"**한 번의 요청으로 여러 개의 SQL 명령을 연속 실행하는 기법**"임.

**특징**
- 세미콜론(`;`)으로 쿼리를 구분
- 데이터 조회뿐 아니라 **삽입, 수정, 삭제, 권한 변경** 등도 가능
- DBMS와 설정에 따라 가능 여부가 크게 다름
- 성공하면 다른 기법보다 훨씬 강력한 행위가 가능

**동작 원리**

원래 하나의 쿼리만 실행되는 곳에\
공격자가 입력값으로 다음을 넣음.
```
'; DROP TABLE users -- -
```
그러면 데이터베이스는
1. 원래 쿼리를 끝내고
2. `DROP TABLE users`라는 **새로운 쿼리**를 이어서 실행함.

**예시 흐름**
1. Stacked Query 가능 여부 확인
```
'; SELECT 1 -- -
```
또는 시간 지연으로 확인 :
```
`; WAITFOR DELAY '0:0:5' -- -
```

2. 데이터 조작
```
'; UPDATE users SET password='hacked' WHERE username='admin' -- -
```

3. 데이터 삭제 또는 추가
```
'; DROP TABLE users -- -
'; INSERT INTO users (username, password) VALUES ('attacker', '1234') -- -
```

**정상 쿼리** :
```
SELECT * FROM products WHERE id = 'userInput';
```

**공격자 쿼리** :
```
SELECT * FROM products WHERE id = '1'; UPDATE users SET password='hacked' WHERE username='admin' -- -'
```
- 첫 번째 쿼리 : 상품 조회
- 두 번째 쿼리 : admin 비밀번호를 `hacked`로 변경

한 번의 요청으로 **조회 + 수정**이 동시에 일어남.

**장점과 한계**

**장점**
- 단순 조회를 넘어 **데이터 변경, 삭제, 계정 생성** 등이 가능
- 한 번의 요청으로 여러 명령을 실행
- 성공하면 피해 규모가 매우 큼

**한계**
- DBMS가 여러 문장 실행을 허용해야 함
- 많은 최신 환경에서는 기본적으로 막혀 있음
- WAF나 입력 필터가 `;`를 차단하는 경우 많음

**정리**
Stacked Queries는
"**세미콜론을 이용해 원래 쿼리 뒤에 새로운 SQL 명령을 붙여 연속 실행하는 기법**"임.

다른 SQLi 기법보다 **훨씬 직접적이고 파괴적인** 행위가 가능하지만,\
환경에 따라 사용할 수 없는 경우가 많음.
